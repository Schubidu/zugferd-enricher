# Browser-local EN16931 validation feasibility

**Status:** proof of a viable open-source execution engine on synthetic CII data;
**not yet bundled into the production browser app** and **not export approval**.

## Goal and constraints

The ZUGFeRD Enricher processes arbitrary third-party invoices exclusively on the
end device. PDF bytes, structured amounts, names, addresses and invoice texts may
**never** be sent to a server for validation, and there is no hidden fallback to
a public API. A validator must be independently tested against the **official**
ZUGFeRD 2.5.2 / Factur-X 1.09.2 EN16931 XSD and Schematron/XSLT resources.
No handwritten substitute for hundreds of business rules is acceptable.

## Independent reference

GitHub Actions uses **Mustangproject CLI 2.26.0**, pinned to SHA-256
`42d7868cb68264874a7b8cab4c3587b03b23ccc7cd72373da917f66758bb9736`,
as a **test oracle only**, never as a browser dependency. The required schemas and
the CEN and profile Schematron XSLTs are extracted from this exact verified JAR.

Official FeRD [ZUGFeRD 2.5.2](https://www.ferd-net.de/publikationen-produkte/publikationen/detailseite/zugferd-252-deutsch)
is the authoritative release. FeRD states that technical XSD and Schematron
artefacts are licensed under **Apache-2.0**:
[usage rights](https://www.ferd-net.de/ueber-uns/ressourcen-1/veroeffentlichungen/haftungsausschluss-und-nutzungsrechte).
The distribution's provenance and licensing notices must be retained when
the assets are eventually bundled. These experiments deliberately do **not**
commit the 29 MB specification archive or any PDF sample invoice.

## XSD feasibility — proven in CI

`.github/workflows/browser-xsd-feasibility.yml` runs
`scripts/probe-browser-xsd.mjs` with **libxml2-wasm 0.7.2**, MIT-licensed,
installed for this job only (no production dependency).

1. Collect all **four** independently versioned EN16931 XSD files.
2. Check every relative `schemaLocation` resolves to an in-memory resource;
   reject remote URLs, directory traversal, DTD and missing dependencies.
3. Register an `XmlBufferInputProvider` so schema parsing cannot depend on
   network access or the host filesystem.
4. Compile the actual EN16931 schema from these buffers, validate the genuine
   synthetic CII generated by `buildCiiCandidate`, and verify **two distinct,
   well-formed but schema-invalid CII variants** are rejected.
5. Explicitly `dispose()` the schema/document/validator objects to release
   WebAssembly memory.

First successful run:
[WASM XSD feasibility #43863413523](https://github.com/Schubidu/zugferd-enricher/actions/runs/43863413523).
**22 ms** for the local XSD probe and **72 MB** Node process RSS were observed
on a GitHub Linux runner. These are **not Safari or iPhone metrics**.

## Schematron feasibility — proven for targeted synthetic scenarios in CI

`.github/workflows/browser-schematron-feasibility.yml` runs
`scripts/probe-browser-schematron.mjs` with **@tradik/xslt3 1.0.0**,
BSD-3-Clause, also installed only for the test job.

- Both untouched official XSLT files execute with an in-memory-only stylesheet
  and XML document resolver: `EN16931-CII-validation.xslt` (CEN rules) and
  `FACTUR-X_EN16931.xslt` (Factur-X profile rules).
- The resolver **must return actual XML `Document` nodes** for
  `document('...')` codelist references, never raw strings. The latter
  caused `XPTY0019` in the first trial; this was fixed without modifying
  either official rule file.
- An apparently successful transformation is never sufficient: it must return
  a real SVRL `schematron-output`, have `fired-rule` elements and zero
  `failed-assert` for the valid sample.
- A corrupted grand total must produce the official **BR-CO-15 / BR-CO-16**
  violations. The wider regression extends this to corrupted tax and line
  amounts, without accepting a no-op transformation.

First successful execution of **both** rule sets:
[Browser Schematron #43865855595](https://github.com/Schubidu/zugferd-enricher/actions/runs/43865855595).
The valid sample fired **58 CEN** and **62 Factur-X** rules with zero failures;
the invalid total generated **BR-CO-15 and BR-CO-16** in both.

## Not yet satisfied

The product has deliberately **not** added these libraries to `package.json`,
the lockfile, Vite or the release bundle. The test runner's temporary npm
installs and JAR extraction are not runtime features.

Before integration:
1. Independently verify the **official FeRD release files** and notices against
   the pinned Mustang-derived test set; ship only the necessary, hashed
   EN16931 XSD, XSLT and codelist resources **inside** the Vite application.
   No runtime fetching from GitHub, a public CDN or Maven Central.
2. Add exact pinned dependencies and lockfile; run the two engines in a
   dedicated Worker with a defined memory budget and cancellation, and fail
   closed if any resource/engine initialization fails. No server-side fallback.
3. Extend the **same** positive/negative corpus across the local engines and
   the independent Mustang oracle: source VAT categories, mixed rates, municipal
   pass-through, discounts, rounding, invoice dates, unsigned/duplicate schema
   resources, and attacks involving external entities or remote `document()`.
4. Verify Safari/iPhone initialization, repeated run memory and end-to-end
   offline operation. Do not assume successful Node/WebAssembly execution
   guarantees Safari behavior.
5. Independently validate the final PDF/A-3 derivative and the **complete
   original PDF vs embedded XML**, including rendered graphics and all lines.

`assessExportPreflight().exportAllowed` remains deliberately `false`.
Neither XSD success nor Schematron success is permission to generate an
unverified ZUGFeRD processing copy.
